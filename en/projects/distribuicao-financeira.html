The problem

People who try to organise their finances in a spreadsheet quit in the third week. What is missing is a simple place to split income by category, follow what is already paid and see what is left — without turning into accounting. And the app has to work in a lift, on a bus, with no signal, because that is where the expense actually gets entered.

What was built

  • Percentage split of income across 6 fixed categories and up to 4 the user creates, adding up to 100%
  • Works offline: the entry lands immediately and uploads itself when the connection returns
  • Debts with three growth rules — fixed instalment, fixed monthly increment or compound interest
  • Frozen monthly close — changing a percentage today does not rewrite last month
  • Recurring rules that repeat each cycle without re-entry
  • Subscription through Google Play, with a free trial and renewal handled by webhook

Architecture

  • Monorepo with an independent NestJS API and Expo app, linked by types generated from the API's OpenAPI spec
  • Backend with global guards — authentication, distribution scope, trial control and rate limiting live outside the controllers
  • Validation through Zod instead of class-validator, with the same schema serving as DTO and as documentation
  • App built on Expo Router, Context API and a local SQLite layer in the outbox pattern
  • Idempotent writes: every operation carries its own id, and a replay returns the same response instead of duplicating the entry
  • Optimistic concurrency through a version field on syncable entities
  • Money as integer cents and percentages as basis points — never floating point, anywhere in the schema
  • Scheduled jobs to materialise the monthly cycle, execute deletions and purge old data

Technical challenges

The app has to work with no signal

Logging an expense takes thirty seconds and almost always happens away from wifi. The app writes locally to SQLite and queues the mutation in an outbox with its own id, retry count and backoff; the backend stores the result of the first execution and returns the same response if the operation arrives again. Reconciliation is not one single rule: server wins by default, client wins for expenses and extra income, and shopping-list items are merged — with the option to undo an automatic adjustment the user did not want.

A closed month cannot change

A month's distribution base — salary plus extra income received — has to be computed, frozen and never touched again, even if the user changes the percentages in January. Solved with an immutable snapshot materialised exactly once per distribution and month through an idempotent upsert, plus a cycle record that stops the close from running twice.

Three different debts in one record

A debt can carry a fixed instalment, a fixed monthly increment in cents, or compound monthly interest in basis points. Three distinct financial behaviours in the same model, and only one can be active at a time — a rule the schema enforces, not the application code.

Two devices, the same account

A user can have more than one distribution and use the app on more than one phone. A dedicated guard resolves which distribution is in use on each request, and a version field on nearly every syncable entity stops a late write from one device from silently overwriting a newer change made on the other.
