Eventa Pro

Running-event platform with two sides: organisers build the event, its distances, price tiers and coupons; runners sign up, pay by instant transfer or card, get a digital ticket with a QR code and later download results and certificates. The platform keeps a fee and controls the payout.

The problem

Race organisers run sign-ups through a form and take payments by hand — no ticket, no seat control, no idea what is left after the fee. At the start line, someone checks names on printed paper. The runner, on the other side, has nowhere to see whether the entry actually counted.

What was built

  • Date-based price tiers inside each distance, with seat control and discount coupons
  • Payment by instant transfer or card, with a gateway webhook and refunds
  • Digital ticket with a QR code — check-in and kit pickup on race day
  • Results and PDF certificates, with public verification by number
  • Per-event team roles: grant check-in access without opening the finances
  • Organiser payouts with the platform fee frozen at payment time

Architecture

  • Monorepo with a NestJS API organised by feature module and a React front split by domain — public, participant, organiser and admin
  • DTOs validated with Zod, and global guards for authentication, role and event ownership
  • Provider interfaces for email and storage: SMTP can be swapped for a self-hosted server, or one image host for another, without touching the rest
  • Frontend HTTP client generated from the OpenAPI spec published by the API
  • Gateway webhook with per-event deduplication — the same notice arriving twice does not charge twice
  • Money as integer cents and the fee in basis points, never decimal
  • Recurring jobs (expire holds, reconcile payments, purge logs) running in-process, with no external queue

Technical challenges

The last seat, two people at once

Two simultaneous sign-ups for the last seat of a distance cannot both succeed. Creation runs inside a transaction that only increments the counter if a seat is still free at that instant — if the condition fails, the whole operation is rolled back. More seats than the limit are never sold, even under concurrent requests. The same mechanism protects each coupon's usage limit.

The abandoned cart that holds a seat

A sign-up holds the seat for 15 minutes waiting for payment. If the runner walks away, that seat cannot stay locked forever. A routine sweeps expired holds, cancels each one with no risk of processing the same record twice and returns the seat to both the distance and the price tier, all inside a transaction.

Paid and never got the ticket

Between the gateway confirming the payment and the system issuing the ticket there is a window where anything can fail. A reconciliation routine looks for confirmed payments left without a ticket and reissues idempotently. Together with webhook deduplication, the runner gets the ticket once — and always.

All the money lands in one account

The gateway does not split the payment between platform and organiser, so tracking who is owed what is the system's job. The fee is computed in basis points, rounded so cents are not systematically lost, capped so it never exceeds what was charged — and frozen at payment time, so changing the fee tomorrow does not rewrite yesterday's financial history.
