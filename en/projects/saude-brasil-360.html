The problem

Federal primary-care funding depends on indicators each municipality has to calculate, prove and hit. The data exists — scattered across every team's electronic health record — but reaches the manager too late and too aggregated: a single percentage closed at the end of the term, when nothing can be fixed any more, and which never says who still needs care.

What was built

  • Calculation of the C1–C7 primary-care indicators following the Ministry of Health's official methodology
  • Oral health (B1–B6), multi-professional teams and state co-funding indicators
  • Named patient lists for outreach — the health agent knows who to visit today
  • Generation of BPA and RAAS, the official billing documents of the Brazilian public health system
  • Partial tracking through the term, not just the closing result
  • Per-module permission matrix with 15 user profiles and geographic restriction by municipality

Architecture

  • Monorepo with frontend, API and a dedicated repository for indicator queries and methodology
  • Feature-based organisation on both ends: each module carries its own layers (Routes → Controller → Service → Repository)
  • Real multi-tenancy: beyond the main database, the backend opens dynamic connections per municipality code to each city's health-record database
  • Versioned snapshots per municipality and period — the indicator is published, not recomputed on every request
  • Leader election via a database lock to coordinate scheduled jobs across multiple instances
  • Observability with OpenTelemetry, per-request correlation id and structured logging

Technical challenges

Calculation bound to official methodology

Every indicator follows a technical note from the Ministry of Health. Instead of recomputing the metric on every request — which would mean scanning the entire municipal population each time — I built a generic snapshot service pattern, reused by around 15 different indicators: the result is published and versioned per period, which gives historical auditability and removes the recompute.

One database per city hall

Each municipality runs its own health-record instance with its own credentials. The backend has to open and keep separate connections per municipality code. The first version created a fresh connection on every request and leaked them; I replaced it with a factory with cache, TTL and a hard cap on concurrent connections.

Scheduled jobs with several instances running

The application runs across multiple instances under a process manager. A naive cron would fire the nightly sync N times at once. Solved with leader election via a table lock and a heartbeat: only the owning instance renews the lock, and another takes over on its own when the leader dies.

Data that arrives dirty

The citizen base coming from city halls has the same person registered more than once, with conflicting national ids. The duplicate-records module normalises the documents and flags merged records so the municipal team can resolve duplicates without losing history.
